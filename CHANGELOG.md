# Changelog

## [Unreleased]

### Added

- `CustomerMethods::dontHaveCartInDatabase()` removes a customer's WooCommerce session and persistent cart from the database, so a cart written on `shutdown` after the database restore no longer returns at login ([#81](https://github.com/aztecweb/aztecweb-wp-browser/issues/81)).
- `CustomerMethods::dontHaveSessionsInDatabase()` removes every WooCommerce session, guests included ([#81](https://github.com/aztecweb/aztecweb-wp-browser/issues/81)).
- `WooCommerceWebDriver` config keys `cartPageSlug`, `checkoutPageSlug` and `myAccountPageSlug`, defaulting to `/cart`, `/checkout` and `/my-account`, and `legacyOrderStorage`, defaulting to `false` (HPOS). A slug that is not a string fails with a `ModuleException`. See the `WooCommerceWebDriver` entry under **Changed** for when a suite has to set them ([#48](https://github.com/aztecweb/aztecweb-wp-browser/issues/48), [#50](https://github.com/aztecweb/aztecweb-wp-browser/issues/50)).
- `OrderMethods::dontSeeOrderInDatabase()`, the order counterpart of `dontSeeSubscriptionInDatabase()` ([#59](https://github.com/aztecweb/aztecweb-wp-browser/issues/59)).
- `OrderMethods::dontSeeOrderMetaInDatabase()`, the order counterpart of `dontSeeSubscriptionMetaInDatabase()` ([#17](https://github.com/aztecweb/aztecweb-wp-browser/issues/17)).
- `skills/write-woocommerce-tests`, an agent skill for writing Cests with this library, and the README section *Writing tests with an AI coding agent*, which installs it with `npx skills add aztecweb/aztecweb-wp-browser/skills/write-woocommerce-tests`. The skill reads the method docblocks from the installed `vendor/` tree, so it follows the library version the project uses ([#44](https://github.com/aztecweb/aztecweb-wp-browser/issues/44), [#39](https://github.com/aztecweb/aztecweb-wp-browser/issues/39)).
- README section *Speeding up the suite*: environment-agnostic guidelines to cut acceptance suite time — log-in over HTTP, wp-admin update checks answered locally, background requests off, `pageLoadStrategy: eager`, a cheap database restore, PHP sizing, and the races a fast suite surfaces.
- `$I->fastLoginAs($username, $password)` and `$I->fastLoginAsAdmin()` sign a user in over the HTTP layer: they POST the credentials to `wp-login.php` with Guzzle in a single request (no redirect following), then copy the returned auth cookies into the browser, HTTPS (`wordpress_sec_*`) included. The log-in flow costs ~0.25 s instead of the ~2–3 s of the browser-driven form, needs no `WPDb` and no wp-config salts, and still lets WordPress do the authenticating ([ADR-0010](docs/adr/0010-fast-login-over-http.md)).
- `Aztec\WPBrowser\Normalizer\StatusNormalizer` — the single helper behind the WC status change described under **Changed**: it prefixes a known bare WooCommerce status with `wc-` and returns anything else untouched ([#19](https://github.com/aztecweb/aztecweb-wp-browser/issues/19)).
- A `notify` job on the runner image workflow that opens — or comments on, once it exists — an issue when a *scheduled* build fails. Nobody watches the schedule, so failures accumulated silently while the image stopped being refreshed; manual runs are excluded, since whoever dispatched one is already watching it.
- `composer test:hooks`, running the file-to-Cest map tests in `.githooks/test-pre-push.sh`, wired into the static-analysis workflow. Nothing executed them before, so the map could drift out of the tree unnoticed.
- `@phpstan-type` shape aliases (unsealed, with enum literals for status/stock/discount values) for the high-arity `overrides`/`criteria` params on `ProductMethods::haveProductInDatabase`/`haveManyProductsInDatabase`, `CouponMethods::haveCouponInDatabase` and its percentage/fixed-cart/fixed-product/free-shipping wrappers, and `OrderMethods::haveOrderInDatabase`/`haveManyOrdersInDatabase`/`haveOrderAddressInDatabase`/`seeOrderAddressInDatabase`/`haveOrderItemInDatabase` — so PHPStan (already at level max over `src` and `tests`) flags hallucinated keys/values in any Cest ([#37](https://github.com/aztecweb/aztecweb-wp-browser/issues/37)).

### Fixed

- `haveOrderInDatabase()`, `haveManyOrdersInDatabase()` and `haveSubscriptionInDatabase()` failing with `table wp_posts has no column named status` when given the `status` key under Legacy storage, and with `table wp_wc_orders has no column named post_status` when given the `post_status` key under HPOS storage. The queries already translated one key into the other, but creation wrote the key as given. Both keys are now accepted under both storages; when both are given, the one of the active storage wins.
- Under HPOS storage, the order and subscription meta methods (`haveOrderMetaInDatabase()`, `grabOrderMeta()`, `seeOrderMetaInDatabase()`, `haveSubscriptionMetaInDatabase()`, `grabSubscriptionMetaFromDatabase()`, `seeSubscriptionMetaInDatabase()`, `dontSeeSubscriptionMetaInDatabase()` and the `meta` key of `haveOrderInDatabase()` and `haveSubscriptionInDatabase()`) wrote and read `wp_postmeta`, which WooCommerce does not read for HPOS orders. They now use `wc_orders_meta`, keyed by `order_id`. A test that seeded or checked HPOS meta in `wp_postmeta` directly has to move to `wc_orders_meta`. Meta criteria accept `order_id`, `subscription_id` and `post_id` as the same key under both storages ([#17](https://github.com/aztecweb/aztecweb-wp-browser/issues/17)).
- `SubscriptionMethods::grabSubscriptionFieldFromDatabase()` under HPOS storage read the subscription's placeholder row in `wp_posts`. It now reads `wc_orders`, so the field is a `wc_orders` column such as `status` or `billing_email`; `post_title` and the other `wp_posts` columns work only under Legacy storage ([#70](https://github.com/aztecweb/aztecweb-wp-browser/issues/70)).
- The admin order page tests taking about 45 s on a local checkout, where the order page ended in `Maximum execution time of 30 seconds exceeded`. `resources/install.sh` dumped the live database every time it ran, so a re-run after the suite saved what the last test had left, such as the Action Scheduler action WooCommerce queues to fetch marketplace suggestions. `sqlite3 .dump` cuts a text value at its first NUL byte, which PHP writes in serialized objects, so the action came back unreadable, and every WooCommerce admin page then tried to cancel it in an endless loop. The script now rebuilds the site from an empty database on every run and refuses to dump a value holding a NUL byte, and the test site's mu-plugin turns marketplace suggestions off. A fresh database also sent the first wp-admin page of a test run within 30 seconds of the script to the WooCommerce setup wizard, so the script now deletes the transient behind that redirect.
- `restartBuiltInServer()` failing with `Port 8080 is already in use.` when another `bin/test` command ran on the same checkout during the suite. `bin/test` deleted `tests/_output/*.pid` before every command, so the restart found no server to stop. It now deletes them only before a Codeception run, and the restart fails at once with a message naming the missing PID file.
- Intermittent acceptance-suite failures in continuous integration with `no such table: wp_options` before a test. WPDb reloads the SQLite file in place before each test, while the page left by the previous browser test could still send requests to WordPress, and a request the server had already received, such as WooCommerce's cart fragments, kept running against a half-restored database. The suite's `Acceptance` helper now replaces the page with `about:blank` after every test and then requests a static file; the single-worker built-in server answers it only once the earlier requests are done. `restartBuiltInServer()` waits the same way before killing the server, since a server killed while writing to SQLite left a journal that was rolled back onto the next test's database. The helper also clears every cookie in the browser through the DevTools protocol, since WebDriver only deletes the cookies the current page can see and a log-in cookie scoped to the `/wp/` path reached the next test.
- Acceptance suite hanging for ten minutes and failing its first test with `SessionNotCreatedException: Timed out receiving message from renderer` on the PHP 8.0 runner image. Chromium 102, pinned in that image, crashes its separate network process while starting in about one session out of twenty, and chromedriver then waits for a page that never loads. The suite now starts Chromium with `--enable-features=NetworkServiceInProcess`, which keeps the network service inside the browser process: 300 consecutive sessions started without a hang, against 17 hangs in 200 before.
- The weekly build of the test runner image, failing since the schedule was introduced: `resources/install.sh` ran before Composer, so the SQLite drop-in the script copies had not been installed yet and every run died at *Bootstrap WordPress* with `cp: can't stat '…/sqlite-database-integration/db.copy'`. While it failed nothing was republished, leaving continuous integration and every developer machine on the last published image. Dependencies are now installed first, and the acceptance suite runs against the freshly built image before the multi-architecture pass pushes it.
- `.githooks/pre-push` now runs every container command through `bin/test`, which forwards the calling user and group. It invoked `docker` directly before, so the image's uid 1001 met a checkout owned by the host user and the hook died on `fatal: detected dubious ownership`, then on `composer.lock: Permission denied`. Its dependency step also moved from `composer update` to `composer install`: a verification gate has to run against the locked versions and leave `composer.lock` untouched in the working tree of whoever is pushing.
- Impacted-test selection in `.githooks/pre-push`, which had stopped selecting anything: the file-to-Cest map pointed at paths the tree no longer had, so no changed file resolved to a Cest and every push quietly ran the full suite instead. Two or more impacted Cests are now passed as a `--filter` anchored at the class boundary rather than positionally, which `codecept run` rejects beyond the first test; a mapped Cest missing from disk and a filter that selects no test both fail the push, where the latter used to be reported as a pass; and a changed file under `src/` that no rule claims widens the run to the full suite rather than leaving the selection untouched.
- `ActionMethods::grabActionsFromDatabase()` always returned an empty array, so negative assertions such as `assertCount(0, ...)` passed whether or not the action existed. It now returns the matching rows through `grabEntriesFromDatabase()`, in a single query ([#68](https://github.com/aztecweb/aztecweb-wp-browser/issues/68)).
- `ActionMethods::haveActionInDatabase()` no longer inserts the `extended_claim_id` column, which Action Scheduler does not define and made every call fail with `Unknown column` ([#68](https://github.com/aztecweb/aztecweb-wp-browser/issues/68)).

### Changed

- **Breaking:** `seeProductInCart()`, `dontSeeProductInCart()` and `seeCartItemQuantity()` take the product name shown on the cart page instead of the product ID, so the browser module no longer looks the name up in the database. Pass the title the product was created with: `$I->seeProductInCart('Test Product')` ([#49](https://github.com/aztecweb/aztecweb-wp-browser/issues/49)).
- **Breaking:** `WooCommerceWebDriver` no longer reads the database and no longer requires `WPDb` in the suite; only `WPWebDriver` ([ADR-0008](docs/adr/0008-webdriver-store-shape-via-config.md), [#51](https://github.com/aztecweb/aztecweb-wp-browser/issues/51)). What it used to look up is now declared in `suite.yml`:
  - Page slugs come from the `cartPageSlug`, `checkoutPageSlug` and `myAccountPageSlug` config keys instead of the WooCommerce pages in the database. A store whose cart, checkout or account page has another slug must set the key, or `amOnCartPage()`, `amOnCheckoutPage()` and `amOnMyAccountPage()` open the wrong page ([#48](https://github.com/aztecweb/aztecweb-wp-browser/issues/48)).
  - `amOnAdminOrderPage()` builds the order URL from the `legacyOrderStorage` config key instead of detecting HPOS in the database. A store on Legacy order storage must set `legacyOrderStorage: true`, or the method opens the HPOS order screen ([#50](https://github.com/aztecweb/aztecweb-wp-browser/issues/50)).
- `CartMethods::amOnCartPage()` now waits for the Cart block to render, as `amOnCheckoutPage()` already did for the Checkout block. The block renders the cart in the browser after the page loads, so `seeProductInCart()` and the other cart assertions could read the page before the items were in it and fail intermittently. The wait ends when the block has dropped its `is-loading` class and none of its inner blocks still shows a loading placeholder (`CartPageObject::LOADING_CART_SELECTOR`), and returns at once on a cart page without the block.
- WC statuses are now accepted with or without the `wc-` prefix wherever an order or subscription status goes **into** the library. That covers `OrderMethods::haveOrderStatus()`/`SubscriptionMethods::haveSubscriptionStatus()`, the `status`/`post_status` key of `haveOrderInDatabase()`/`haveManyOrdersInDatabase()`/`haveSubscriptionInDatabase()`, and the status criterion of `seeOrderInDatabase()`, `dontSeeOrderInDatabase()`, `grabOrderIdFromDatabase()`, `seeSubscriptionInDatabase()`, `dontSeeSubscriptionInDatabase()`, `grabSubscriptionIdFromDatabase()` and the `seeOrderStatus()`/`seeSubscriptionStatus()` helpers built on them — under both HPOS and Legacy storage. `$I->seeOrderStatus($id, 'processing')` and `$I->seeOrderStatus($id, 'wc-processing')` are now the same assertion. Normalization is not validation: an already-prefixed status, a third-party plugin status and a WordPress post status such as `trash` all pass through verbatim. Reads are deliberately untouched — `grabOrderStatus()` and `grabSubscriptionStatus()` still return the raw stored value, `wc-` prefix included — and the coupon status methods, which take a WordPress post status, are unaffected. Pre-1.0 behavioral change, shipped without a feature flag ([ADR-0009](docs/adr/0009-wc-status-normalization-on-input.md), [#19](https://github.com/aztecweb/aztecweb-wp-browser/issues/19), [#20](https://github.com/aztecweb/aztecweb-wp-browser/issues/20), [#21](https://github.com/aztecweb/aztecweb-wp-browser/issues/21), [#22](https://github.com/aztecweb/aztecweb-wp-browser/issues/22)).
- `CartMethods::addProductToCart()` no longer waits for the "product added to cart" notice: it issues the add-to-cart request and returns. The notice is a one-shot session notice — cleared on print, and lost whenever anything rewrites the WooCommerce session between the add-to-cart request and the render (async loopbacks, a persistent object cache, a plugin touching the session) — so the wait timed out on runs where the product had in fact been added. There was nothing left to synchronize: `amOnPage()` returns only once the add-to-cart request has been served, and no other element is guaranteed to exist on every landing page a store can choose. Tests that assert on cart contents must navigate first, with `amOnCartPage()` or `amOnCheckoutPage()`; the method itself stays agnostic to the store's "Add to cart behaviour" setting and to the `woocommerce_add_to_cart_redirect` filter ([#66](https://github.com/aztecweb/aztecweb-wp-browser/issues/66)).

### Removed

- `OrderStorageInterface::getAdminOrderEditUrl()` and its HPOS and Legacy implementations. The admin order URL is built by `Aztec\WPBrowser\WooCommerce\Browser\AdminOrderUrlResolver` from the `legacyOrderStorage` config key ([#50](https://github.com/aztecweb/aztecweb-wp-browser/issues/50)).
- `Aztec\WPBrowser\WooCommerce\Config\WooCommerceConfig`, which resolved the page slugs from the database; they are module config now ([#51](https://github.com/aztecweb/aztecweb-wp-browser/issues/51)).
- `CartPageObject::PRODUCT_ADDED_TO_CART_MESSAGE_SELECTOR` — the notice it targeted is no longer waited on by any method in the package. Projects that overrode it to point at cart state can drop the override ([#66](https://github.com/aztecweb/aztecweb-wp-browser/issues/66)).

## [0.1.0] - 2026-06-09

### Added

- `LICENSE` — MIT license (copyright 2026 Aztec Online) ([#2](https://github.com/aztecweb/aztecweb-wp-browser/issues/2)).
- Expanded `composer.json` distribution metadata: richer `description`, `keywords`, `homepage`, `authors`, `support.issues`/`support.source`, and `config.sort-packages` ([#2](https://github.com/aztecweb/aztecweb-wp-browser/issues/2)).
- Static-analysis baseline: PHPStan at level max and PHPCS (PSR-12 plus a curated Slevomat ruleset), exposed via a `composer check` script ([#3](https://github.com/aztecweb/aztecweb-wp-browser/issues/3)).
- Custom PHPCS sniff `RequirePublicMethodDocBlockSniff` (`src/CodeSniffer/Sniffs/`) enforcing wp-browser-style docblocks with an `@example` tag on every public method of Plugin Modules (`*\Module\`) and Method Traits (`*\Method\`) ([#7](https://github.com/aztecweb/aztecweb-wp-browser/issues/7)).
- PHPDoc backfill across all public methods of the Plugin Modules and Method Traits using the full wp-browser skeleton (summary → `@example` → `@param` → `@return` → `@throws`) ([#7](https://github.com/aztecweb/aztecweb-wp-browser/issues/7)).
- `src/aliases.php` — Class Alias Trick so consumers can reference the Plugin Modules by short name (`WooCommerceDb`, `WooCommerceWebDriver`) in `suite.yml` ([#6](https://github.com/aztecweb/aztecweb-wp-browser/issues/6)).
- `.githooks/pre-push` — pre-push hook that runs the impacted acceptance tests before pushing, mapping changed traits to their Cest classes and falling back to the full suite for shared-infrastructure changes ([#5](https://github.com/aztecweb/aztecweb-wp-browser/issues/5)).
- Slim test runner image (`Dockerfile`) shipping PHP, Chromium, chromedriver, SQLite and Composer. WordPress, WooCommerce and the library source come from a bind-mount of the repo — the image does not bake any app code, so a rebuild is only needed when the system-level toolchain changes.
- Composer-managed WordPress tree under `public/` (`roots/wordpress-no-content`, WooCommerce, Storefront, sqlite-database-integration, `wp-cli/wp-cli-bundle`) wired through `composer/installers`. `vendor/bin/wp` is the canonical WP-CLI entrypoint.
- `bin/test` wrapper that runs any command inside the image with the repo bind-mounted at `/var/www/html`.
- `bin/serve` wrapper for launching the site in a browser during manual inspection.
- `resources/install.sh` — idempotent script that bootstraps the SQLite WordPress site (`wp core install`, plugin/theme activation, HPOS sync), with the WP-CLI calls collapsed to four.
- `.github/workflows/acceptance.yml` — CI workflow that runs the acceptance suite against PHP 8.0 and 8.4 on every push and pull request, using the published GHCR runner image.
- `.github/workflows/build-test-runner.yml` — manual-trigger workflow (`workflow_dispatch` only) that builds the image for both PHP variants and pushes to GHCR as `${repo}-runner:php{N}` plus an immutable `:vYYYYMMDDThhmmssZ-php{N}` content tag. Automatic triggers (push, cron) are deferred to [#13](https://github.com/aztecweb/aztecweb-wp-browser/issues/13).
- Consumer-facing `README.md`: requirements, installation with the `suite.yml` snippet (short-form and FQN fallback), quick-start Cest, a per-domain method index across `WooCommerceDb` and `WooCommerceWebDriver`, an HPOS note, an architecture paragraph linking the ADRs, and local-development/contributing sections ([#8](https://github.com/aztecweb/aztecweb-wp-browser/issues/8)).
- Two Plugin Modules — `WooCommerceDb` (database helpers) and `WooCommerceWebDriver` (browser helpers) — with every WooCommerce concern organised under the `Aztec\WPBrowser\WooCommerce\` subnamespace, and Action Scheduler under its own `Aztec\WPBrowser\ActionScheduler\` subnamespace with the `ActionMethods` trait ([#6](https://github.com/aztecweb/aztecweb-wp-browser/issues/6)).
- PSR-4 autoloading for the `Aztec\WPBrowser\` namespace, including the `Aztec\WPBrowser\Tests\Support\` → `tests/_support/` prefix so `dump-autoload --strict-psr` is clean ([#2](https://github.com/aztecweb/aztecweb-wp-browser/issues/2)).
- `composer.json` pins `config.platform.php` to `8.0.0` so dependency resolution targets the minimum supported PHP version, and caps `symfony/filesystem`/`symfony/process` to `<8.0` so `composer update` resolves Symfony 6.x under PHP 8.0 (matching `lucatume/wp-browser` constraints). The acceptance CI uses `composer update` instead of `install` so each PHP variant resolves packages compatible with its runtime.
- `codeception.yml` enables `BuiltInServerController` and `ChromeDriverController` plus the `lucatume/wp-browser` dev commands (`dev:start`, `dev:stop`, `dev:restart`, `dev:info`, `wp:db:import`, `wp:db:export`, `run:original`, `run:all`).
- SQLite-backed acceptance suite: `tests/acceptance.suite.yml` runs against the sqlite-database-integration drop-in with chromedriver on `localhost`, `public/wp-config.php` defines `DB_ENGINE` (default `sqlite`) to engage the plugin from a single switch, and `wp-cli.yml` points at the `public/wp/` core install.
